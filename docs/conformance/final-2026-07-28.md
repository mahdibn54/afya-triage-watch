# Conformance report: afya-mcp and the api's MCP client on protocol 2026-07-28 (E13-4 final)

Protocol-conformance probe with the official framework. It is **not** AAIF certification and **not** a clinical
validation: it says nothing about triage safety, scoring correctness or the clinical record. Application and security
behaviour stays covered by the project's own tests (mcp, api, evals, `scripts/smoke.sh`).

## Reproduce (no secrets)

```
pip install -e "mcp[dev]" -e "api[dev]"
# afya-mcp behind a throwaway OFFLINE issuer (in-memory key, per-mount token injected; nothing is fetched or printed)
PYTHONPATH=mcp python -m uvicorn conformance_app:app --app-dir scripts --port 9100 &
CT="npx -y @modelcontextprotocol/conformance@0.2.0-alpha.12"
for m in read act ui; do
  $CT server --url http://localhost:9100/$m/mcp --requirements 2026-07-28 \
      --expected-failures docs/conformance/expected-failures.yaml -o out/server-$m
done
PYTHONPATH=api $CT client --command "python scripts/conformance_client.py" --requirements 2026-07-28 \
    --expected-failures docs/conformance/expected-failures.yaml -o out/client
python scripts/conformance_report.py out/server-read out/client      # markdown tables
```

The tool cannot send headers, so for the protocol scenarios `scripts/conformance_app.py` adds a short-lived token for the
requested mount (its audience and scope only) to requests that carry none. Real token validation (signature, issuer,
audience, expiry, scope, 401/403 challenges, RFC 9728 metadata) is covered by `mcp/tests/test_auth.py` (30 tests) and by
`scripts/smoke.sh` against the live Authelia.
Exit code with the expected-failures file: 0 only when every failure is in the list and every listed scenario still
fails (a listed scenario that starts passing fails the run until the entry is removed). The three server runs and the
client run all exit 0 on this tree; a negative control (a passing scenario listed as expected) exits 1.

## Triage of every failure

Legend: **DEFECT** = our code, **SDK** = behaviour of mcp 2.3.0, **FIXTURE** = the tool's reference server has a tool,
prompt or resource that afya-mcp deliberately does not offer, **NOT-OFFERED** = optional feature we do not implement,
**NA** = does not apply to this implementation. Full list with reasons: [expected-failures.yaml](expected-failures.yaml).

### Server (per mount, identical)

| Scenarios | Class | Why |
|---|---|---|
| `tools-call-image/audio/embedded-resource/mixed-content/with-progress`, `json-schema-2020-12` | FIXTURE | tools only on the reference server; afya-mcp has 3 (read) / 4 (act) / 3 (ui) text tools |
| `resources-read-text/binary`, `resources-templates-read` | FIXTURE | `test://...` resources; afya-mcp offers no resources (the unknown-resource error path itself passes `sep-2164`) |
| `prompts-get-*` (4) | FIXTURE + SDK | no prompts. mcp 2.3.0 answers an unknown prompt with -32603 "Internal server error" instead of -32602 (SDK maps the `ValueError`). Not patched: SDK internals, no prompt is ever used |
| `completion-complete` | NOT-OFFERED | no completions capability |
| `input-required-result-*` (10 failing + 2 warnings) | FIXTURE | multi-round-trip flows need `test_input_required_*` tools; no afya-mcp tool asks the client for input. The two WARNs judge the "Unknown tool" answer to a fixture call |
| `http-custom-header-server-validation` | NOT-TESTABLE | no tool carries `x-mcp-header`, so no custom-header rule can be exercised |
| `server-stateless`: `sep-2575-server-rejects-undeclared-capability`, `sep-2575-missing-capability-http-400` | FIXTURE (the earlier "missing-capability" flag) | needs the diagnostic tool `test_missing_capability`; we answer "Unknown tool" and the check reads that as "executed". No afya-mcp tool needs a client capability, so there is nothing to reject; this is **not** shown to be a defect, and also not shown to pass |
| `tasks-*` (9 failing) | NOT-OFFERED | Tasks extension, optional, not scored by the tool; all tools are synchronous |

### Fixed in this story (the earlier "whitespace header" flag): real defect, fixed

`http-header-validation` / `sep-2243-server-accepts-whitespace-header-value` failed on all mounts: `Mcp-Name: "  compute_tews  "`
was answered 400 / -32020 because mcp 2.3.0 compares the raw header with the body. RFC 9110 section 5.5 makes the
surrounding whitespace not part of the value. Fix: `TrimMcpHeaders` in `mcp/afya_mcp/server.py`, an ASGI wrapper per mount that strips
spaces and tabs around the value of `Mcp-*` request headers (inside the OAuth check, so authentication and the Host/Origin
checks are unchanged); a genuinely different name is still refused 400 / -32020. Test:
`mcp/tests/test_discovery.py::test_whitespace_around_mcp_header_values_is_accepted`. Result: `http-header-validation` now passes (14 checks, 0 failing).

### Known, not fixed: the SDK advertises empty `prompts` and `resources`

`server/discover` and `initialize` report `capabilities.prompts` and `capabilities.resources` (with `listChanged`/`subscribe`
false) although afya-mcp registers neither: the SDK derives capabilities from handlers it always installs, and has no
public switch. `prompts/list` and `resources/list` return empty lists (those scenarios pass), so no client is misled
in practice, but the advertisement is inaccurate. Not patched (it would rewrite SDK internals or post-process every
response); recorded as a known limit, to revisit with a newer SDK. `mcp/tests/test_discovery.py` asserts the current honest shape
(`tools` static, `resources.subscribe` false, no logging/completions/tasks/extensions).

### Authorization

The tool has **no server-side scenario for an OAuth resource server**: its authorization scenarios are client
scenarios (`auth/*`) and authorization-server scenarios (`conformance authorization`, which exercise an authorization-code
grant against an AS). Therefore:

- Resource-server behaviour of afya-mcp (RFC 9728 metadata, 401 + `WWW-Authenticate: resource_metadata`, 403
  `insufficient_scope`, audience, expiry, signature) is **not** measurable with this tool; evidence is
  `mcp/tests/test_auth.py` and `scripts/smoke.sh`. `AFYA_CONFORMANCE_AUTH=off` (no injected token) was run to confirm what the
  tool then sees: every request gets 401 with `resource_metadata` and `scope`, the RFC 9728 document is served, and the
  tool's server scenarios cannot proceed (expected, not counted as a result).
- `conformance authorization` targets an authorization server; ours is third-party (Authelia 4.39.28, selected in E13-3) and
  configured for `client_credentials` only, while the tool's `authorization-code-grant` needs a browser redirect flow. Not run, not applicable.
- Client leg: the api is a service client. `auth/client-credentials-basic` (extension, not scored) and
  `auth/pre-registration` pass with the api's real provider. The other `auth/*` scenarios need the authorization-code flow,
  PKCE, CIMD or dynamic registration, step-up, `offline_access` or issuer-parameter handling, none of which the api implements
  (callers are services; nobody signs in to MCP), so they fail in the driver and are classified NA. They are listed as expected failures, never as passes.
  Consequence worth knowing: `auth/resource-mismatch`, `auth/metadata-issuer-mismatch` and the `iss-*` checks were
  "not testable" in this driver; the api's issuer pinning and resource binding are covered by `api/tests/test_mcp_client.py`, not by this tool.

| Scenario | Class | Why |

## Not claimed

- No AAIF (Agentic AI Foundation) certification or listing, no claim of "fully conformant". 24 required server scenarios and
  25 required client scenarios fail, all documented above as fixture, not offered or not applicable; none is a pass.
- Conformance results come from an **alpha** tool, not a stable release.
- Server protocol scenarios ran behind a test issuer with an injected token; OAuth resource-server conformance is not covered by this tool.
- No clinical validation, no safety or accuracy claim. Synthetic data only; the run touches no database or FHIR server.
